## Configuration

Create a Blueprint from this repository's main branch, or use these equivalent Web Service settings:

| Setting | Value |
|---|---|
| Runtime | Python 3.12.14 |
| Instance | Free; one instance |
| Region | Ohio |
| Build | `pip install --require-hashes -r requirements.lock` |
| Start | `gunicorn "src.app:create_app()" --bind 0.0.0.0:$PORT --workers 1 --threads 4 --timeout 60 --access-logfile - --error-logfile -` |
| Health check | `/health` |
| Auto deploy | After CI checks pass |

Render provides the PORT variable. SECRET_KEY and ADMIN_SETUP_TOKEN are independently generated by Render. COOKIE_SECURE must be true for the HTTPS deployment; the local HTTP setting remains separate. Supply MONGODB_URI, MONGODB_DATABASE and ADMIN_USERNAME privately in Render's environment settings. Copy the already verified Atlas URI from the ignored local .env; do not paste it into source, Blueprint YAML, a screenshot, an issue or the AI log. Never upload the .env file to GitHub.

SKELETON_PASSWORD is used by local fixture setup, not read by the running web app, and does not need to be uploaded to Render. Existing Atlas demo accounts retain their password hashes. The public demo's new SECRET_KEY intentionally does not reuse local sessions.

## Atlas network access

From the created Render service, open Connect → Outbound. Allow the exact displayed outbound CIDR ranges in Atlas Network Access. Keep the existing development-machine entry if local access is still needed. These are region-shared egress ranges, not a private network; Atlas still requires database credentials and TLS. Do not substitute 0.0.0.0/0. A failed initial deploy due to missing network access can be retried after the displayed ranges are allowed.

The target Atlas database has already received migration 0001 locally. This deployment only verifies its schema on startup; it does not migrate, reseed, reset passwords or delete demonstration data on each deploy. For a different empty database, explicitly run the documented migration/setup against that dedicated database before starting. Do not use the destructive repeatable-demo seed command on a database containing real user data.

## Verification

1. Confirm the deployment is Live in Render and /health returns HTTP 200 with status ok.
2. Open /login over HTTPS. Sign in with an existing fictional Atlas demo user using the private demo password. Confirm the unit page renders persisted messages and events.
3. Confirm session cookies have Secure, HttpOnly and SameSite=Lax. POST without CSRF must fail; an anonymous unit request must redirect to sign-in.
4. Open the HTTPS URL on a separate device to complete the requested cross-device check. localhost/127.0.0.1 URLs are not public links.

The public app allows registration, but new users initially have no units; a unit owner/leader must add their usernames. Administrator registration requires the configured ADMIN_USERNAME and the Render-specific ADMIN_SETUP_TOKEN. The local setup token is not the hosted setup token. Keep administrator tokens and database passwords private.

The existing iteration-1 tag and recording are preserved. Free instances can sleep when idle; allow startup time on the first request.
